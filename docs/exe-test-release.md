# 固定 EXE 测试版

浏览器继续使用开发目录和 Vite 实时更新。EXE 测试版仅在一个大版本或完整功能完成、用户明确要求同步后发布；不设定时更新、不自动构建、不刷新活动游戏。

## 两个入口

- 双击根目录 `更新EXE测试版.cmd`，或运行 `npm run release:test`：从当前工作区复制快照并生成新版 EXE。首次使用也需要先执行一次。构建不会启动游戏。
- 双击根目录 `启动EXE测试版.cmd`，或运行 `npm run start:test`：只打开最近一次成功发布的 EXE；没有发布版时提示先发布，绝不回退到开发服务器。

这两个脚本需要已安装的 Node.js 和项目依赖。现有 `npm run dev` / `npm run electron` 仍是开发入口，打开的 Electron 窗口会连接 Vite，不能当作固定测试版。

测试包采用免安装的 EXE 目录版，路径是 `.exe-releases/<版本ID>/app/win-unpacked/wuxian-lunhui-test.exe`。也可以直接双击这个 EXE；不要单独移动 EXE，旁边的资源和运行库必须一起保留。不走原 portable 单文件压缩链，避免每次本地测试都重复制作安装/自解压包。

## 日常工作流程

1. 用户在固定 EXE 中测试；Codex 在开发目录修改，浏览器实时更新。
2. 用户反馈，完整功能开发完毕后，再明确说“同步更新 EXE 测试版”。功能完成本身不触发发布。
3. 发布前协调其他会话：快照包括工作区未提交修改，复制期间不要编辑代码、配置和资产。复制完成后的打包只读取快照中的游戏内容；构建工具使用本机已安装依赖，期间也不要升级依赖。
4. 发布成功才替换 `latest.json` 启动指针；失败继续指向上一版。每次使用全新版本目录，不修改已发布包，不重启任何活动进程。
5. 旧测试版正在运行时，启动新版只聚焦旧窗口。测试结束并保存、退出后，再用启动入口进入新版。

游戏右下角标识显示“固定测试版”、项目版本号和唯一版本 ID。反馈问题时带上该 ID；即使没有递增 package.json，仍可区别两次发布。每版 `release.json` 记录时间和参考提交号；因为包含未提交修改，提交号不代表完整内容，`source/` 才是本次游戏源码与素材快照。

## 数据和资源隔离

- 全部游戏 JS、CSS、图片、音频和 JSON 都从本版包内读取；不用开发服务器、不用硬链接或目录联接。打包 EXE 即使继承 `NODE_ENV=development` 也不会连接 Vite。
- 固定通道使用 `%APPDATA%/wuxian-lunhui-fixed-test`，升级时不清空、不覆盖。开发浏览器和旧 Electron 的数据保持原样；首次使用固定通道会是独立存档，旧通道存档不自动迁入。
- 固定页面地址始终为 `wl-test://game/index.html`，资源由 Electron 映射到当前包的 `dist`。本地存档的 origin 不随版本目录变化，切换固定版后仍使用相同存档空间。
- 调试面板写入只进入测试通道用户数据目录，不回写开发目录。用户自己保存过的配置覆盖项会继续生效，反馈配置差异时应同时说明这些修改。
- 升级只保留已保存的数据，不迁移正在进行的战斗内存状态；存档兼容性仍取决于对应游戏功能。回退旧版代码不等于回退存档，跨存档格式升级前应在退出后另行备份测试数据目录。

## 发布边界

新的发布脚本不调用原 `npm run build`，不递增源码版本号、不执行旧备份清理、不写共享 `dist` 或 `dist-electron-new`。原构建命令保留，不能用它们替代固定测试版发布。

`.exe-releases/` 不纳入 Git，也被当前 Vite 的隐藏目录忽略规则排除。每次发布会保留快照、构建输入和成品，磁盘占用会是资源体积的数倍；不会自动清理旧版。确认不再使用后，可手动清理指定旧版本目录，勿删除正在运行的版本或 `latest.json` 指向的版本。

发布采用单任务锁。如果系统强制终止发布，可能留下 `.exe-releases/publishing.lock`；确认没有发布任务后再移除该文件重试。失败生成的目录不会成为默认启动版本。
