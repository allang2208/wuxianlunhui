# 多世界并行系统方案（2026-08-18）

> 目标：世界-122（基地防守）与世界-123（雪原）等世界同时运转——玩家在 123 时，
> 122 的波次/产兵/采矿/研究继续推进。本文档为评估与方案，尚未实施。

## 1. 现状架构（调研结论，含文件证据）

- **单场景激活**：`switchScene`（scene-manager.js:93-248）离场时逐系统 teardown +
  `Game.entities.clear()` 全清（:168），入场 `_loadScene8/9` 从零重建。
  **玩家摆放的墙/门/塔/建筑离场即消失，重进不恢复**（只有主神空间有 `_mainEntities` 快照）。
- **单一全局实体表**：`Game.entities`（game.js:98）承载当前场景全部实体；分离碰撞、
  小地图、深度仲裁、研究刷新等直接读写它。
- **单例子系统**：DefenseSystem/EnergyNode/Hut/Barracks/Producer/Miner 全是模块级单例，
  状态挂单例，teardown 即销毁；波次/产兵/研究读条全在建筑实例上，teardown 丢进度。
- **计时语义**：几乎全部 dt 驱动（切走即冻结）；献祭是唯一真实时间（30 分钟 expiresAt）。
- **世界-123 现状**：纯观景雪地（scene-manager.js:1198-1259），复用 122 地形管线，
  不 setup 任何 122 子系统；传送门建筑已占位（producer-buildings.json portal）。
- **存档**：主存档 `world122` 字段只有全局商店状态（升级/研究/能源/献祭），
  无场景态、无建筑态、无波次进度（game-ui-manager.js:280-298）。

## 2. 开销评估

### 单世界-122 当前帧耗结构（实体 60~200+：54 矿点 + ≤40 怪 + 建筑 + ≤5/建筑的兵）

| 开销项 | 性质 | 位置 |
|---|---|---|
| 实体逐个 `update(dt)` + AI（120ms 决策） | O(n)，无距离裁剪 | game.js:1382 |
| 分离碰撞 | **O(n²) 双重循环**，每对还带 WallSystem.resolve | game.js:1754-1901 |
| 空间分区每帧重建 | O(n) | game.js:1354 |
| GameScene 每帧 5+ 次全表同步（深度仲裁/小地图/结构排序/阴影/闪白） | O(n) 渲染侧 | GameScene.js:1213/6543/6594 |

渲染由 Phaser 相机裁剪，单世界时不是瓶颈；**逻辑层无离屏休眠，122 单世界已接近舒适区上限**。

### 两个世界天真同跑的代价（不改造直接并行）

- **逻辑**：若合并到一张实体表，O(n²) 分离从 200²=4 万对/帧 → 400²=16 万对/帧（**4 倍不是 2 倍**）；
  GameScene 全表同步同步翻倍 → 帧耗近似 ×2~×4，60fps 难保。
- **渲染**：若只渲染玩家所在世界、后台世界纯逻辑，渲染不翻倍（唯一省下的部分）。
- **结论**：天真并行不可行；但**按世界分表后逻辑开销降为 2×n²（线性叠加）**，
  再叠加降频/抽象模拟可压到 1.0~1.2 倍。

## 3. 业内方案对照

| 方案 | 业内实例 | 适用性 |
|---|---|---|
| 兴趣管理（按玩家相关性分级模拟） | MMO 标配（WoW 区域服务器） | 前台全精度、后台降精度——正是我们的前后台结构 |
| 降频/分时模拟（time-slice + tick 分级） | EVE Online Time Dilation；RTS 低逻辑帧率 | 后台世界 1~5Hz 低频 tick，前台 60fps 不变 |
| 事件驱动/抽象结算（挂机收益模型） | 放置类/SLG（率土之滨攻城计时、AFK Arena 离线收益） | 后台不逐实体模拟，只推进计时器+按速率结算，回场一次性 catch-up |
| 确定性回放（lockstep 命令流） | 星际争霸/War3 | 对本项目过重，不推荐 |
| Web Worker 线程卸载 | 大型 H5 游戏（逻辑/渲染分线程） | M3 可选：后台世界逻辑进 Worker，快照消息回传；序列化成本高，先做 M1/M2 |
| 空间分区宽相 | 本项目已有 SpatialPartitionSystem（每帧重建） | 分离碰撞 O(n²)→就近网格查询，单世界就受益，是并行的前置优化 |

## 4. 推荐路线（分层递进）

### M0（前置，必做）：世界状态快照与恢复
- per-world 实体快照序列化（建筑位置/HP/读条、波次进度、矿点剩余、单位），存档加 `worlds.{id}` 字段。
- 解决"离场即丢失"——这是任何并行方案的地基，且独立有价值（122 重进不再从零）。
- 计时统一改造：读条类（研究/产兵/波次）从纯 dt 改为「锚点时间戳 + dt」双模，
  离场记锚点、回场结算——与献祭 expiresAt 同口径。

### M1（推荐首个并行形态）：前台全真 + 后台抽象低频
- 玩家所在世界照常全精度模拟；后台世界**不建实体**，每 1s 一次抽象 tick：
  产兵/研究/矿工产出按速率累计；波次按时间轴推进为"战报事件"（如 W3 已刷出、进攻中），
  战斗用兵力对比简化结算（参考塔 DPS×数量 vs 波次 HP 池），矿点按速率减储量。
- 玩家回场时按快照+抽象状态**重建实体**（building 血量、在读条、当前波次、存活单位数）。
- 开销：后台每帧 <0.1ms；实现集中在各系统的"抽象 tick"分支，不动主循环。

### M2（需要更高保真时）：后台具象低频
- 后台世界保留 per-world 实体表，逻辑 2~5Hz 跑（无渲染、无深度仲裁、无小地图），
  实体 AI/寻路照旧但时间片分摊到多帧；分离碰撞换空间网格（前置优化）。
- 需要完成"单例系统 → per-world 实例槽"改造（最大工作量点）。

### M3（远期可选）：Worker 线程
- 后台世界逻辑进 Web Worker，主线程只收状态快照做事件提示；Phaser 渲染不进 Worker。

### 无关系列的前置性能优化（先做，单世界也受益）
1. 分离碰撞 O(n²) → 复用 SpatialPartitionSystem 网格宽相（game.js:1754）。
2. GameScene 全表同步降频/缓存（深度仲裁按移动实体增量、小地图 100ms 节流）。
3. 实体休眠带：8000px 外的矿点/散件不 update（agent 实测现在全图无差别 update）。

## 5. 风险与注意点

- **玩家唯一性**：相机/输入/RTSCommand/波次门控硬绑当前场景（game.js:1415），
  M1 下不动；M2 起需解耦"玩家世界"与"模拟世界"。
- **战斗保真度**：M1 抽象结算可能与实机结果有偏差——建议先用"兵力估值模型"，
  回场若偏差大则该波重置为"即将来袭"（补偿性重打），用户可接受度高。
- **献祭口径**：已按真实时间，并行后天然兼容，无需改。
- **存档兼容**：worlds.{id} 新字段，旧档回退为"仅当前世界"，无迁移风险。
- **工作量粗估**：M0 ≈ 2~3 天（快照+计时改造）；M1 ≈ 2~3 天；M2 ≈ 1 周+（实例化改造）；
  M3 单列。前置优化 1~2 天。
