## 15. Git 分支、worktree 与标准提交工作流

本工作流适用于会创建、修改或删除仓库文件的任务。目标是让 `main` 上的每个提交都对应一个完整、可审查、可独立回滚的逻辑任务，同时允许各任务分支保留开发检查点。

用户明确要求只查看、不提交、采用其他分支策略或扩大/缩小提交范围时，以用户当次要求为准。本工作流不改变项目的测试授权边界：用户没有明确要求测试时，不运行测试、构建、lint、浏览器探针或运行时验证。

### 15.1 基本单位

- **提交单位是逻辑任务，不是会话。** 一个任务跨多个会话时继续使用同一任务分支；一个会话完成多个无关任务时拆分提交。
- `main` 上默认一个人物、功能、修复或独立资产交付对应一个干净提交。只有多个部分具有独立回滚价值时才保留为少数几个提交。
- 开发分支允许检查点提交；修正优先使用 `fixup!`，合入前整理或 autosquash。
- 禁止为了减少数字而定期重写共享 `main`。普通增长通过合入时 squash 控制；全历史重写只用于误入敏感文件、超大二进制或经用户批准的专项治理。

### 15.2 多任务并行隔离

- `main` 工作区只用于同步和整合，保持干净；每个独立人物或任务使用一个 `codex/<scope>` 分支和一个独立 worktree。
- 不同任务不得共享同一 worktree；同一分支也不得同时挂载到多个 worktree。
- 同一人物跨会话继续复用该人物的分支/worktree。不同人物分别建立分支，例如 `codex/character-redwolf`、`codex/character-jaguar`。
- 公共角色框架、共享注册表或基础协议的大改动单独建立 `codex/character-framework`，先合入 `main`，再让人物分支基于新主线继续。
- 遇到共享工作区已有未知改动或 `.git/index.lock` 时，不切分支、不删除锁、不提交、不清理；改用独立 worktree，或等待占用该工作区的会话收口。
- 全历史改写完成后，旧 worktree/分支不得直接继续推送；应从新 `main` 重建或明确迁移其有效提交。

创建示例：

```powershell
git worktree add ..\game-dev-redwolf -b codex/character-redwolf main
git worktree add ..\game-dev-jaguar -b codex/character-jaguar main
```

### 15.3 文件归属与暂存铁律

- 只处理、暂存和提交本任务明确拥有的文件或代码块；其他会话的改动一律保留，不排查、不修复、不顺手提交。
- 脏工作树中禁止使用 `git add -A`、`git add .`、`git commit -a`。使用 `git add -- <精确文件>`；同一文件混有他人改动时使用 `git add -p`。
- 暂存前后都必须查看真实 diff。发现无法可靠拆分的未知重叠改动时，停止提交并说明冲突，不得猜测归属。
- 禁止用 `git reset --hard`、`git checkout --`、`git clean` 或整文件覆盖清除未知改动。
- `data/` 与 `public/data/` 中受双份同步合同约束的配置，必须作为同一逻辑提交一起暂存。

### 15.4 资产提交边界

- 已选正式资产、运行时接线和必要 provenance/提示词属于交付；明确废案、未选候选、缓存、可重建中间物和临时预览不进入 Git。
- 正式资产与代码只有在能够独立回滚时才拆成两个提交；否则作为一个人物/功能提交共同落地。
- 不因文件较大就自行启用 Git LFS 或改变仓库存储协议；需要迁移时先由用户确认。

### 15.5 每次提交的固定步骤

#### 第 1 步：确认上下文

查看当前分支、工作树、近期提交、`CHANGELOG.md` 和相关 `SKILL.md` 分卷，确认任务基线、文件范围和不能破坏的项目合同。

```powershell
git branch --show-current
git status --short
git log -5 --oneline
```

#### 第 2 步：建立隔离

确认当前位于本任务专属 `codex/<scope>` 分支/worktree。共享 `main` 有未提交改动、锁文件或正在被其他会话使用时，不在其中开展新任务或提交。

#### 第 3 步：声明提交范围

在动手前确定：本任务拥有的文件、预期提交数量、验收行为，以及是否会触碰共享配置。范围变化时先重新划分，不把顺手修改混入提交。

#### 第 4 步：完成一个逻辑单元

实现必须达到可独立理解和回滚的状态。未完成内容留在任务分支继续开发，不以“会话结束”为由提交到 `main`。

#### 第 5 步：审查本任务真实 diff

仅查看本任务文件和必要调用链，确认没有混入格式化噪声、生成缓存、废案或其他会话改动。普通交付不扩展成全仓审计。

```powershell
git diff -- <本任务文件...>
```

#### 第 6 步：遵守验证授权

只有用户当次明确授权测试时才运行相称的测试/构建/运行时验证；否则直接进入暂存，并在交付中明确写明未测试、由用户测试。

#### 第 7 步：精确暂存

```powershell
git add -- <本任务文件...>
```

同一文件存在混合归属时改用：

```powershell
git add -p -- <文件>
```

#### 第 8 步：核对暂存区

提交前必须检查暂存文件清单和完整暂存 diff；发现多余文件或未知代码块时先移出暂存区，不带病提交。

```powershell
git diff --cached --name-status
git diff --cached
git diff --cached --check
```

#### 第 9 步：提交并回报

沿用仓库的 Conventional Commit 风格：

```text
feat(units): add jaguar warrior
fix(combat): preserve attack target during movement
assets(world122): add approved barracks sources
docs(git): define standard commit workflow
```

提交后核对提交摘要和实际文件，不把工作树中其他会话仍未提交的改动误报为本次提交内容。

```powershell
git show --stat --oneline --summary HEAD
git status --short
```

交付汇报必须列出：提交哈希与主题、提交文件/行为、未提交的并行改动是否仍保留、测试或运行时验证状态、需要用户重点验证的风险。

### 15.6 合入主线

- 人物/功能完成后先同步当前 `main`，在任务分支解决冲突；不得在脏的共享 `main` 上直接 rebase 或强行合并。
- 默认通过 squash merge 让一个逻辑任务在 `main` 留下一个提交。需要独立回滚的少数提交可原样保留。
- 多人物依次合入；每合入一个人物，后续人物分支先更新到新 `main` 再合入，逐步消化共享文件冲突。
- 合入并确认 worktree 没有未提交内容后，才移除对应 worktree 和已合并分支。
- `--force-with-lease` 仅用于所有并行会话已经收口、备份已校验且用户明确批准的历史改写；普通功能合入禁止强推共享主线。

### 15.7 停止提交的条件

出现以下任一情况时，只完成安全范围内的工作并向用户说明，不创建提交：

- 当前工作区存在无法确认归属的重叠改动；
- 存在 `.git/index.lock` 或明确有其他会话正在操作同一工作区；
- 暂存区包含本任务范围外文件，且不能安全拆分；
- 合并冲突尚未逐项确认；
- 提交会依赖尚未合入的共享协议，或会迫使回退他人改动；
- 用户明确要求只查看、只审计或不要提交。
